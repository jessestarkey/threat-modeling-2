# Threat Catalogue

This catalogue lists every threat category that this framework can identify, across the three
layers of the risk engine:

| Layer | Count | Description |
|---|---|---|
| Built-in rules | 35 | Threats detected by the underlying threat-modeling platform itself |
| Extension rules | 62 | Threats added through the platform's own extension mechanism |
| Organization-specific categories | 86 | IL5-specific threats defined and injected by this organization's own risk engine |
| **Total** | **183** | |

The platform's seven model-authoring checks are left out. They flag mistakes in how a model was
built (an incomplete model, an asset or link that is defined but never used, or content that does
not match what a model element claims to be), not security threats, so they have no meaningful
likelihood or impact to catalogue.

## How to read each table

Threats are grouped into tables by focus area: Identity, Device and Infrastructure, Network and
Environment, Application, Artificial Intelligence, Data, Detection, Response, Recovery, and
Governance. Not every layer produces threats in every focus area. Each row gives two things in
particular:

- **Technology / Attribute / Behavior:** the technology, attribute, or behavior that causes the
  threat to be identified on a system component.
- **Likelihood / Impact:** the starting rating for the threat class, before any adjustment for
  the component it is found on. All three rule layers were calibrated to one rubric on 2026-11-18
  (see the Risk Methodology document, "Risk calibration").

To keep the tables scannable, the reasoning behind each rating is collected in the
[Appendix](#appendix-likelihood-and-impact-justifications), in the same order, and it is grounded
in MITRE ATT&CK, CAPEC, and OWASP where a genuine mapping exists. Likewise, the meaning of each
Technology / Attribute / Behavior term is collected in the
[Glossary](#appendix-technology--attribute--behavior-glossary).

Every statement in this catalogue traces to the engine's configuration. Where the source material
has no written justification for a rating, or no genuine ATT&CK, CAPEC, or OWASP mapping applies,
the appendix says so plainly rather than inventing one.

## Methodology

A starting rating is not the final score reported for a finding, since every finding takes two
further adjustments:

- **Likelihood** moves up or down with how attractive a target the component is, which depends on
  the sensitivity of the data it handles and what it can reach. It also rises one level when the
  component is reachable from the internet, in the built-in and organization-specific layers.
- **Impact** moves up or down one level with the component's own confidentiality, integrity, or
  availability rating, whichever the threat endangers. Injection and code execution threats use
  the higher of confidentiality and integrity. The same adjustment applies in all three layers.

The system's overall mission criticality does not raise any rating. Every component carries its
own justified confidentiality, integrity, and availability rating, so a system-wide increase
would mostly inflate minor components that happen to share a system with important ones. Thus, a
component that matters more than its rating suggests should have that rating corrected instead.
The companion Risk Methodology document gives the full reasoning.

## Open issues

Building this catalogue surfaced two issues, and neither is changed by this document:

- The built-in unencrypted-asset rule requires both confidentiality and integrity to be rated high
  before it fires, even though its own description says either one is enough. As a result, a
  component that holds highly sensitive data but has only moderate integrity is not flagged.
- Several extension-layer threats have sound starting ratings but no written explanation of why
  that rating was chosen, and the appendix notes where this is the case.

## Appendix: Likelihood and Impact Justifications

This appendix gives the reasoning behind every Likelihood and Impact rating above, grouped by the
same focus areas and in the same order, so a threat can be looked up by name.

Each entry ends with a **Calibrated 2026-11-18** note, which gives the current starting rating,
the rating on a typical IL5 asset, and the reason. The evidence before the note still stands, but
where that text names a different level, the note gives the current rating. Each note also gives
the finding's class. A *model weakness* is shown by the model's own facts, such as a plain-HTTP
link. In contrast, a *control verification* fires because an interface exists, while the model
cannot show whether the control is in place, so its rating is capped at Likely.

MITRE ATLAS technique IDs, case-study IDs, and case-study counts are as of the ATLAS v5.x data.
However, ATLAS v6 (2026.10) restructured some techniques (for example, AML.T0056, AML.T0057,
AML.T0024.000, and AML.T0024.002 are no longer separate techniques there), and counts drift
between releases.

## Appendix: Technology / Attribute / Behavior Glossary

This appendix defines each Technology / Attribute / Behavior value in the main tables. It has
three tables, which match the three parts of the column header rather than the focus areas:
1. **Technologies** are named system components or platforms, the noun for what something is,
   such as Datastore or Identity Provider.
2. **Attributes** are a property, configuration state, or rating that a technology or connection
   has or lacks, including states of absence, such as Multi-Tenant Deployment or Missing Vault.
3. **Behaviors** are an action, flow, or practice, meaning something done or not done, such as
   Push Deployment or Bulk Data Export.

Each value is defined once, alphabetically within its table, regardless of which focus area's
threats use it. A `Location` column states which layer uses the term (`Built-in platform rule`,
`Extension rule`, `Organization-specific category`, or more than one where layers share a term),
matching the main tables' `Location` column rather than naming individual rules. A few terms
straddle two categories, since a missing or self-managed component is really an Attribute of an
otherwise-named Technology. Each such term is placed where a reader would most likely look for it
first, rather than being listed twice.

Every entry traces to one of four sources: (1) a native Threagile technology type
(`00-threagile-field-reference.yml`), (2) a tag this organization defines (`03-tags-lib.yml`), (3)
a technology attribute native to the `jessestarkey/threagile` fork (`pkg/types/technology-list.go`,
matched by the extension rules in `pkg/risks/scripts/`), or (4) a built-in rule's own detection
logic (`pkg/risks/builtin/`). Where a value is a plain-English description of the check rather than
a named technology, the entry says so.

However, no source is tied to one table, since each can produce a Technology, an Attribute, or a
Behavior. A tag, in particular, is only this organization's general-purpose labeling mechanism,
read by `inject_risks.py`'s trigger logic. For example, `ai:agent-framework` names a kind of
component (the Technology "AI Agent Framework"), `mgmt:self-managed-identity` names a state a
component is in (the Attribute "Self-Managed Identity Infrastructure"), and `ai:user-prompt-input`
names something a component does (the Behavior "Free-Form Prompt Input"). Thus, the table a value
lands in depends on whether it names a *what*, a *property of a what*, or *what it does*, not on
which source produced it.
