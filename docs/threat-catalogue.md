# Threat Catalogue

A complete reference of every threat category this framework can identify, across all three layers of the risk engine:

| Layer | Count | Description |
|---|---|---|
| Built-in rules | 35 | Threats detected by the underlying threat-modeling platform itself |
| Extension rules | 73 | Threats added through the platform's own extension mechanism |
| Organization-specific categories | 87 | IL5-specific threats defined and injected by this organization's own risk engine |
| **Total** | **195** | |

A small additional set of platform rules that check for modeling mistakes (an incomplete model, an asset or connection that was defined but never used, mismatched content between a model element and what it claims to represent) is excluded. Those flag problems in how a model was *built*, not security threats, and have no meaningful likelihood or impact to catalogue the way a real threat does.

## How to read each table

Threats are grouped into tables by security domain (Identity, Device and Infrastructure, Network and Environment, Application, Artificial Intelligence, Data, Detection, Response, Recovery, Governance — not every layer produces threats in every domain). Each row describes:

- **Technology / Attribute / Behavior** — what causes this threat to be identified for a given system component, in plain terms.
- **Applicability Justification** — the reasoning behind that condition.
- **Likelihood / Impact** — the starting rating for this threat class (bolded), followed by its justification, before any adjustment for the specific component it's found on. Justifications are grounded in MITRE ATT&CK, CAPEC, and OWASP where a genuine mapping exists.

Every statement in this catalogue traces to the engine's actual configuration — nothing here is invented. Where no written justification for a rating exists in the source material, or no genuine ATT&CK/CAPEC/OWASP mapping applies, the table says so plainly rather than inventing one.

## Methodology

A baseline rating is not the final score reported for a specific finding. Every real finding gets two further adjustments:

- **Likelihood** is adjusted up or down based on how attractive a target the specific component is to an attacker — a function of the sensitivity of the data it handles and how reachable it is from other parts of the system.
- **Impact** is adjusted up or down based on the specific component's own confidentiality, integrity, or availability rating, matched to whichever of those three the threat actually endangers.

There is deliberately no longer a blanket rating increase applied just because the overall system is rated mission-critical. That adjustment used to exist and was removed after review: in practice it mostly inflated the rating of genuinely minor, peripheral components just because they shared a system with important ones — the opposite of what it was meant to do. Every component in this framework already receives its own individually justified confidentiality/integrity/availability rating; a component that is more important than its own rating suggests should have that rating corrected directly, not compensated for indirectly by a system-wide flag.

See the companion Risk Methodology document for the full reasoning behind this approach.

## A note on what this catalogue found

Building this catalogue surfaced two pre-existing issues worth tracking separately, neither of which has been changed as part of writing this document:

- One built-in threat (unencrypted data at rest) currently requires BOTH confidentiality and integrity to be rated high before it is identified, even though its own written description says either one should be enough. A component holding extremely sensitive data but only moderately-rated integrity is not currently flagged at all.
- A number of extension-layer threats have correct baseline ratings but no written explanation for why that rating was chosen.
